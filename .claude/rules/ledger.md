# Identity, records and randomness (`src/ledger`)

ADRs 0009 and 0010 are the contract. This code runs in browsers, Node and workerd: no DOM, no Node-only APIs.

- The private seed never leaves `identity.ts`, except through the explicit recovery-code export the player triggers. Never log it, send it, put it in records or keep it in another store.
- Records are canonical JSON (RFC 8785) of integers and strings only. Use fixed-point integers (biomass, energy and health in hundredths), never floats. Hashes and signatures always carry a domain tag (`bs/rec/v1`, `bs/hello/v1`, ...).
- UTXO rule: a transition names the creature's current head as `prev` with `seq + 1`. Restoring an ancestor is a new transition; never re-accept an old record.
- Randomness commitments name a future drand round (`latest + 2`) before it exists. No retries, no alternate rounds, no cancel-to-reroll. Never use an unverified beacon.
- Integrity is not legitimacy: verification recomputes seeds, inheritance, time gates and costs, not just hash links.
- Tests use the recorded beacon fixtures in `tests/fixtures/drand/`, never the live drand network.
- Mating (M5): a record kind's allowed successors live in the transition matrix; mate asks are signed by both players and name the commitment round. A stored `birth` must pass `checkBirth` (recomputed from the beacon, the commit id and both parents' genomes), and every record `checkStored`. A player has at most one active and one pending creature.
- Rules versions (ADR 0055): `registry.ts` lists each live version with its world epoch and, per part, the version where that part last changed. Every check answers a version through `rulesStatus` (`rules-retired` below `FIRST_LIVE_RULES`, `rules-unknown` for one this build doesn't list). A rules bump without a world renewal adds an entry; one that changes a part recorded history depends on also keeps that part's older code.
- Typed bodies (rules 11): `bodyProblems` lists every kind's fields and refuses any other (`unknown:<field>`), so a new field is a rules bump. A `mate-commit` keeps the condition after its cost and the one it paid from (`…Before`); a `death` is `{ cause, activeMs, biomass }`, plus `enc` and `by` for `killed` and `eaten`, and `enc` alone for a hazard death a fight's settlement wrote.
- One rulebook (`gates.ts`): lifespan, maturity time and size (both shortened by `Scales.mating` in a test world), cooldown, repeat window, restore minimum, a creature's start, a mating's cost (`paidFor`) and the growth reach, under `Scales` (`LIVE_SCALES` in production). The authority and the verifier call these and nothing else; the reach uses `exp` from `src/sim/math.ts` and is floored to hundredths, so every engine draws the same line (a pinned table is checked in Node and workerd).
- Proof bundles (`proof.ts`, ADR 0055): what `GET /v1/proof` and `GET /v1/fight` serve, read only through `parseProofBundle` and `parseFightProof`, which take untrusted JSON (text or value), cap every list and string (64 creatures, 4,096 records, 512 keys, 1,024 witness commitments, 2,048 attestations, 512 KB of JSON), rebuild each object from checked fields, refuse unknown fields and any record `recordProblems` refuses, and never throw. A bundle is version 2 (ADR 0058): `witnessCommits` (kind `witness`, owner `''`, kept apart from `commits`) and `attestations`; a version 1 bundle parses as version 2 with both empty. A settlement is version 1 (`referee: 'authority'`) or version 2 (`referees`, the spans, and `duty`, the witness commitment's id or `''`); `settlementOf` writes version 2, both parse (`proof.ts` and the wire's enc-end) and verify, and `parseRefereeSpans` checks only the spans' shape, leaving their sense to `refereeSpanProblems` and the witness family.
- The verifier (`verify.ts`): `verifyLineage(bundle, opts)` indexes the bundle (`BundleIndex`) and runs one file per family, each `(index, opts) => Problem[]`: `verify-chain.ts` (chains and signatures), `verify-origin.ts`, `verify-gates.ts`, `verify-fights.ts` and `verify-witness.ts` (which also returns the report's `witnessed` and `events`). It never throws. A problem is `{ creature, seq, family, code }`; every code a family names gets its plain sentence in `PROBLEM_TEXT` (`problemText`), with no raw code in it. The keys in force are `opts.keys` (pinned), else the bundle's, each only when its id derives from its key and from its `from` on; a commitment's key must be in force by the first record that names it. Countersignatures go through `key-verify.ts`, which tables each key once and must answer exactly as `verify` does. The verifier never imports `src/net` at run time: a fight replay comes in through `opts.replay`. The origin family (`verify-origin.ts`) recomputes each held first record through `checkGenesis` and `checkBirth`, checks every genome text against its first record and every commitment's round against its `t`, and reports a birth with a parent outside the bundle as `unchecked`, not as a problem. The gates family (`verify-gates.ts`) walks each chain with the clock, condition and cooldown its records establish; every bound is inclusive, as the authority's, every record of a frozen creature until its restore keeps the clock, condition and cooldown it was frozen with (`frozen-changed`), and a fight's records (and a settlement's checkpoint before a death) get their clock and growth bounds from the fights family. The index keeps every settlement: two for one `enc` are `settlement-duplicate`, and every copy is signature-checked, held to the records and replayed. The fights family (`verify-fights.ts`) ties each record naming an `enc` to a settlement in the bundle (`checkSettledRecords`, as `settled:<field>`), bounds a fight's records (a settlement's checkpoint and its death both from the record before the fight) by the wall time, the slack and the fight's frames, and, with `opts.logs` and `opts.replay`, replays each held log (`replay:<code>`, leaving the countersignature to the signature family) and checks each held fighter's start and locked time against it; `problemText` reads a parameterised code by its longest listed prefix. The witness family (`verify-witness.ts`, ADR 0058) takes each held event (every settlement, each held genesis, each mating a held record names) and, when the bundle holds its witness commitment (the settlement's `duty`, else the one for its event, else the one its attestations name), checks the countersignature (its key in force by the first held record that names the event, as for any commitment: a commitment's own `t` is on the randomness clock, which fixture mode sets apart from the records'), `witnessDataProblems`, the round unpublished at its `t` (a mating's or a genesis's equal to the event's own), its beacon, and the order it draws; then each referee span's witness and each attestation's at its position, each attestation's signature, duty and subject, and each position used once. A disagreeing attestation is overruled, not a problem; an event with neither a witness span nor an agreeing attestation is authority-only; a commitment not held leaves the selection `unchecked`, no pool `none`. Beacons go through `verifyBeacons` (`drand.ts`): one pairing check for the lot with 128-bit Fiat–Shamir coefficients, so forged signatures cannot cancel out, and each alone when it fails; a beacon alone costs about 25 ms.
- `tests/lineage-fixture.ts` is the honest history every verifier test tampers with (A0, B0, their mating, A1 and B1, a fight in which A1 kills B0 and eats B1's egg, a toxin death and a restore), built from the rulebook under the scales it is given. Beside it stand the witness documents of an honest authority: A1's fight refereed by W from frame 40 and audited by V, the mating and A0's genesis audited, B0's genesis authority-only (an empty pool). `bundleOf` serves a subject's bundle as the authority does, and `src/ledger/__golden__/lineage.json` pins A1's. The M8 settlement golden (`settlement.json`) stays version 1, so version 1 keeps verifying. A tamper test re-signs what it changes with the fixture's key (`resign`), so only the check under test can catch it. Never change the honest history to make a family pass.
- Witness documents (`witness.ts`, ADR 0058), all pure and shared. The shapes and parsers that need no key (events, `WitnessData`, attestations, `parseSignedAttestation`) live in `witness-doc.ts`, which `witness.ts` re-exports and the wire's parsers import alone, so the app shell loads no `@noble/curves`. An event is `dutyEvent(kind, id)` (`enc:`, `mating:` or `genesis:` and 64 hex). A pool is at most 16 ids with the lowest `SHA-256('bs/pool/v1' ‖ event ‖ id)`, sorted by id (`poolOf`), checked by `witnessDataProblems`; its round is `witnessRound(t)`, the first due at least 500 ms after `t`. The order (`witnessOrder`) is a Fisher–Yates shuffle through the sim's PRNG seeded by `seedFromBytes(SHA-256('bs/witness/v1' ‖ randomness ‖ the commit id's 32 bytes))`; `tests/witness-order-table.ts` pins one order that Node and workerd both check. Signatures go through `Identity.sign(domain, bytes)`: an attestation (`bs/attest/v1`) signs its canonical JSON with `agree` as 1 or 0; an input (`bs/input/v1`) signs `inputBytes`, the tag, the encounter's 32 bytes, u16 frame and u32 code (49 bytes); a witness frame (`bs/wframe/v1`) signs the tag, the encounter and its `frameLeaf`. A mating's subject is `birthSubject`, SHA-256 under `bs/attest/birth/v1` of both birth hashes in slot order. `parseSignedAttestation` takes untrusted JSON, refuses unknown fields and a `code` beside `agree: true`, and never throws; player keys are checked through `keyVerifier`, tabled once per key (a cache of 64 in `witness.ts`, or the caller's `KeyVerify` for inputs). The drand clock (`QUICKNET`, `roundAt`, `roundTime`) lives in `drand-time.ts`, so the shell and these documents name rounds without loading BLS.
