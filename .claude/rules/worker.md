# Authority Worker (`worker/`)

ADR 0008 is the contract: one Worker and one SQLite Durable Object, minimal by design.

- No game loop and no simulation ticking on a timer. Handle messages and alarms only. Encounter refereeing (M7) runs timers only while a fight is active.
- Budgets:
  - ≤ 1 request-equivalent (20 incoming WebSocket messages) per player-minute outside fights;
  - ≤ 10 SQLite row writes per player-hour.
  Meter usage per UTC day and queue new sessions before any free-tier limit is reached, never after.
- Handlers are idempotent (keyed by transaction hash) and do every state change in a single SQLite transaction. Schema changes are numbered migrations (`worker/schema.ts`), applied in one transaction at start-up; one that needs the time it runs is a function of `(sql, now)`. Migration 6 is the world renewal (ADR 0040): `world` holds the epoch and reset time, `players.epoch_seen` the epoch each identity was told about.
- Use hibernatable WebSockets (`ctx.acceptWebSocket`) and keep per-socket state in attachments. Protocol pings use auto-response so they don't wake the object.
- Accept requests only from the Pages origin and localhost. Validate every message with the shared codecs. Rate-limit each session.
- Secrets (TURN key, the Cloudflare token for deploys) come only from Worker secrets or GitHub secrets. Never put them in code, logs, responses or tests.
- Tests run offline in workerd (`@cloudflare/vitest-plugin`) and through local `wrangler dev`, with drand and Cloudflare APIs faked or replayed from fixtures.
- `Authority` (`worker/authority.ts`) keeps the object's state, the alarm and the message dispatch; the handlers live by area as functions of `Hub` (`worker/socket.ts`, with `Session` and the send helpers): `sessions.ts` (sign-in, admission, ponds, signaling), `lives.ts` (genesis and life), `offspring.ts` (mating and offspring), `engage.ts` (lock-in, and joins into a running fight through `admit` in `fights.ts`; each fighter's worth as prey comes from `worthOf` in `farming.ts`, reads only) and `settle.ts` (a fight's end: its records, each fighter's locked time and the signed settlement through `Ledger.settle` in `ledger-encounter.ts`, then `died` and `enc-end` with the document; a settlement that throws writes nothing, flags `settle-failed`, closes the row and sends each connected fighter `enc-end` without a document, then `life` as the ledger holds it). Locks and running fights live in memory in `fights.ts` (`hub.fights`: the `Referee`, the authority's `Encounter` and one timer per lock for the next deadline), on `hub.clock` (`now`, `after`, `cancel`), which hub tests swap for a hand-moved clock (`useFightHub` in `worker/fight-test-kit.ts`) instead of waiting on real milliseconds. Its `hatched()` dates each identity past the young window, so fights there run at worth 1 unless a test says otherwise (`firstSeenAgo`).
- Fights persist their log (ADR 0053, migration 7): one `encounters` row per fight through `hub.fightStore` (`worker/fight-store.ts`). It is inserted before `enc-start` is sent (a failed insert releases the lock and refuses the attacker `engage:stale`), each join is written before its `enc-join`, the final frames follow every `BATCH_FRAMES` (10, a worker constant) and at once when a participant's socket closes (`drop`), and the settlement's transaction writes the tail, the countersigned document (`settlementOf`) and `open = 0` (`FightStore.seal`, handed to `Ledger.settle` as the `log` of its input). Batch writes leave the indexed `open` column alone, so each costs one row. Its rows count in `ledger.rowsWritten`; hub tests that bound a fight's other writes use `rowsBesideLog` (`fight-test-kit.ts`).
- Recovery (`worker/recover.ts`, M8 T5): the constructor's `blockConcurrencyWhile` runs `recoverFights` after the migrations, and so does the alarm. Each open row the object doesn't hold is rebuilt (the lock, the encounter replayed from the log, the `Referee` restored at the log's length with its joins); each connected participant gets `enc-start` and the history (`resend` in `fights.ts`), and then `tick` finalizes every frame past its deadline with `null`, settling a fight that ends so. A row whose fighters already hold its records (left open by a close before M8 T8, which now closes it in the settlement's transaction), or that no longer rebuilds, is only closed. A lock still waiting for its answer has no row and leaves nothing.
- Sign-in during a fight (M8 T6): a participant of a running fight keeps its seat while away (`awaySeats` in `sessions.ts` counts it in its pond's 24 and in `MAX_SESSIONS`, and its sign-in skips the queue). `enter` seats it in the fight's pond and sends `welcome`, `life` with `fight`, then `resend`. A locked fighter's `progress` is acknowledged with nothing credited or written, and its close writes no checkpoint: the settlement writes its records.
- The object has one alarm slot. Only `Authority.rearm` sets or clears it, as the earliest of the hello timeout, `Beacons.nextDue()`, the 15 s admission-queue tick (held only while someone is queued) and the fights' watchdog (`Fights.watchDue()`: each running fight's frame 0 + the 90 s timeout + 1 s, so an evicted object still wakes to settle it); new alarm users extend it instead of calling `setAlarm`.
- The Worker has two entries: `index.ts` (production, live drand) and `e2e-entry.ts` (recorded rounds, `node tools/worker.mjs dev --e2e`). Fixture code and E2E hooks (`POST /v1/e2e/pre-reset`, M6c T2; `POST /v1/e2e/restart`, M8 T5) live only in the latter; `tools/worker-bundle.test.ts` guards that.
- Hub tests that need beacons swap the live object's `source` field (`worker/test-hub.ts`: `login`, `hatch`, `useFakeBeacons`, `publish(round)` moves a fake clock and runs the alarm), so no test waits for real rounds. Tests that need the wall clock (progress, lifespan) mock `Date.now` (`worker/progress.test.ts`).
- A creature's per-connection state (`LifeState`, `worker/life.ts`) lives in the socket attachment and is written to SQLite only as checkpoint records; keep it small (2 KB limit).
- Admission (`worker/usage.ts`, `canAdmit` in `worker/sessions.ts`): `MAX_SESSIONS` and `DAILY_REQUEST_BUDGET` are `vars`; a hub test sets them on the live object's `env` (`worker/queue.test.ts`). A queued socket has phase `queued` in its attachment and costs no SQLite writes.
- `MATING_SCALE` (fixture mode only, with `DRAND_SOURCE=fixture`) shortens maturity, cooldown and the repeat window; hub tests set it on the live object's `env` (`worker/mating.test.ts`). A courtship's invitation lives in the courting socket's attachment (`court`), never in SQLite; `worker/mating.ts` must export nothing that edits a stored round.
