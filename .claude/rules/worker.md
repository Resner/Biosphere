# Authority Worker (`worker/`)

ADR 0008 is the contract: one Worker and one SQLite Durable Object, minimal by design.

- No game loop and no simulation ticking on a timer. Handle messages and alarms only. Encounter refereeing (M7) runs timers only while a fight is active.
- Budgets:
  - ≤ 1 request-equivalent (20 incoming WebSocket messages) per player-minute outside fights;
  - ≤ 10 SQLite row writes per player-hour.
  Meter usage per UTC day and queue new sessions before any free-tier limit is reached, never after.
- Handlers are idempotent (keyed by transaction hash) and do every state change in a single SQLite transaction. Schema changes are numbered migrations (`worker/schema.ts`), applied in one transaction at start-up; one that needs the time it runs is a function of `(sql, now)`. Migrations 6 and 8 are the world renewals (ADRs 0040, 0055): `world` holds the epoch (3) and reset time, `players.epoch_seen` the epoch each identity was told about; migration 8 also empties `encounters` and the away reports.
- Use hibernatable WebSockets (`ctx.acceptWebSocket`) and keep per-socket state in attachments. Protocol pings use auto-response so they don't wake the object.
- Accept requests only from the Pages origin and localhost. Validate every message with the shared codecs. Rate-limit each session.
- Secrets (TURN key, the Cloudflare token for deploys) come only from Worker secrets or GitHub secrets. Never put them in code, logs, responses or tests.
- Tests run offline in workerd (`@cloudflare/vitest-plugin`) and through local `wrangler dev`, with drand and Cloudflare APIs faked or replayed from fixtures.
- `Authority` (`worker/authority.ts`) keeps the object's state, the alarm and the message dispatch; the handlers live by area as functions of `Hub` (`worker/socket.ts`, with `Session` and the send helpers): `sessions.ts` (sign-in, admission, ponds, signaling), `lives.ts` (genesis and life), `offspring.ts` (mating and offspring), `engage.ts` (lock-in, and joins into a running fight through `admit` in `fights.ts`; each fighter's worth as prey comes from `worthOf` in `farming.ts`, reads only) and `settle.ts` (a fight's end: its records, each fighter's locked time and the signed settlement through `Ledger.settle` in `ledger-encounter.ts`, then `died` and `enc-end` with the document; a settlement that throws writes nothing, flags `settle-failed`, closes the row and sends each connected fighter `enc-end` without a document, then `life` as the ledger holds it). Locks and running fights live in memory in `fights.ts` (`hub.fights`: the `Referee`, the authority's `Encounter` and one timer per lock for the next deadline), on `hub.clock` (`now`, `after`, `cancel`), which hub tests swap for a hand-moved clock (`useFightHub` in `worker/fight-test-kit.ts`) instead of waiting on real milliseconds. Its `hatched()` dates each identity past the young window, so fights there run at worth 1 unless a test says otherwise (`firstSeenAgo`). The ledger dates records on `hub.clock`, and the life clock (`LifeState.t`, its binding and every report's `now`) runs on it too; the hatch bucket, courtship, usage and admission stay on `Date.now()`.
- Fights persist their log (ADR 0053, migration 7): one `encounters` row per fight through `hub.fightStore` (`worker/fight-store.ts`). It is inserted before `enc-start` is sent (a failed insert releases the lock and refuses the attacker `engage:stale`), each join is written before its `enc-join`, the final frames follow every `BATCH_FRAMES` (10, a worker constant) and at once when a participant's socket closes (`drop`), and the settlement's transaction writes the tail, the countersigned document (`settlementOf`) and `open = 0` (`FightStore.seal`, handed to `Ledger.settle` as the `log` of its input). Batch writes leave the indexed `open` column alone, so each costs one row. Its rows count in `ledger.rowsWritten`; hub tests that bound a fight's other writes use `rowsBesideLog` (`fight-test-kit.ts`). Retention (M9 T10, ADR 0056, migration 9): the row's `frames` hold the packed log (`worker/fight-pack.ts`: 4-byte big-endian codes, `0xFFFFFFFF` for the fallback, base64, widths from the start's fighters and the joins; a row written as JSON still reads), which is why the referee refuses code `0xFFFFFFFF`. `FightStore.seal` then prunes (`prune(settlement.t)`): up to `PRUNE_PER_SETTLEMENT` (4) settled rows started `LOG_KEEP_DAYS` (14) or more before, oldest first through the partial index `encounters_kept`, get `start`, `joins`, `frames` and `fighters` blanked (id, pond, `t`, `persisted` and the settlement stay), so `fightProof` answers `log: null` and `FightStore.read` null. A prune never touches records, commitments, beacons or settlements. The usage row's `db_bytes` is `ctx.storage.sql.databaseSize` at the day's first flush, and `GET /v1/audit` shows it as `storage: { bytes, limit }`. `npm run report:storage` regenerates `docs/perf/storage.md`.
- Recovery (`worker/recover.ts`, M8 T5): the constructor's `blockConcurrencyWhile` runs `recoverFights` after the migrations, and so does the alarm. Each open row the object doesn't hold is rebuilt (the lock, the encounter replayed from the log, the `Referee` restored at the log's length with its joins); each connected participant gets `enc-start` and the history (`resend` in `fights.ts`), and then `tick` finalizes every frame past its deadline with `null`, settling a fight that ends so. A row whose fighters already hold its records (left open by a close before M8 T8, which now closes it in the settlement's transaction) is only closed. One that no longer rebuilds (or whose recovery throws) is given up as a failed settlement is: `recover-failed` flagged once, the row closed, the locks released, and each connected participant sent `enc-end` without a document, then `life` as the ledger holds it (`backToLedger` in `settle.ts`). A lock still waiting for its answer has no row and leaves nothing.
- Sign-in during a fight (M8 T6): a participant of a running fight keeps its seat while away (`awaySeats` in `sessions.ts` counts it in its pond's 24 and in `MAX_SESSIONS`, and its sign-in skips the queue). `enter` seats it in the fight's pond and sends `welcome`, `life` with `fight`, then `resend`. A fighter's `progress` while its fight runs (`Fights.playerFighting`) is acknowledged with nothing credited or written, and its close writes no checkpoint: the settlement writes its records. A lock still asking is free play: reports credit, a close writes the checkpoint, and `start` takes each side's latest clock.
- The object has one alarm slot. Only `Authority.rearm` sets or clears it, as the earliest of the hello timeout, `Beacons.nextDue()`, the 15 s admission-queue tick (held only while someone is queued) and the fights' watchdog (`Fights.watchDue()`: each running fight's frame 0 + the 90 s timeout + 1 s, so an evicted object still wakes to settle it); new alarm users extend it instead of calling `setAlarm`.
- Proof reads (M9 T7, ADR 0055): `GET /v1/proof/<creature>` and `GET /v1/fight/<enc>` are checked in `index.ts` (origin as `publicJson`, then 400 `id` for anything but 64 lowercase hex), answered from `caches.default` when it holds the path (a hit never reaches the object), else by the RPCs `Authority.proof` and `Authority.fight`, and their 200, 404 or 413 is cached without CORS headers (`MAX_AGE`: a day for a settled fight, 10 minutes for a dead creature's bundle, else 60 s). The object counts each one in the usage meter (`usage.request`) and answers 503 `busy` past 80% of `requestBudget(env)`. `worker/proof.ts` reads SQLite itself and only reads (every query adds its `rowsWritten` to the ledger's count, so a test sees none): `proofBundle` walks the ancestors breadth-first (nearest first, ties by id, through each birth's parents and each child `promote`'s chain parent) and cuts each at its last tie to a held child (`mate-commit`, parent `promote`, or the death of a chain parent that died first), growing through `Growth` (sizes and record counts kept per added creature, so a bundle is assembled once) and stopping at 64 creatures or before 512 KB or 4,096 records with `more` naming the parents left out; a subject whose own chain passes the caps is `413 too-big` (the card says "too long to check here", the CLI exits 2); it reaches only creatures that the subject's records name. `fightProof` serves the settlement and the row's log (the pond seed is the settlement's), null until settled. Keys are read from `keys` directly: a proof read never makes one.
- The Worker has two entries: `index.ts` (production, live drand) and `e2e-entry.ts` (recorded rounds, `node tools/worker.mjs dev --e2e`). Fixture code and E2E hooks (`POST /v1/e2e/pre-reset`, M6c T2; `POST /v1/e2e/restart`, M8 T5; `GET /v1/e2e/encounter/<id>`, M8 T9) live only in the latter; `tools/worker-bundle.test.ts` guards that.
- Hub tests that need beacons swap the live object's `source` field (`worker/test-hub.ts`: `login`, `hatch`, `useFakeBeacons`, `publish(round)` moves a fake clock and runs the alarm), so no test waits for real rounds. Tests that need the wall clock (progress, lifespan) mock `Date.now` (`worker/progress.test.ts`).
- A creature's per-connection state (`LifeState`, `worker/life.ts`) lives in the socket attachment and is written to SQLite only as checkpoint records; keep it small (2 KB limit). Its bounds hold per record interval (ADR 0055, as the verifier checks them): the credit since the last record (`boundT`, `boundMs`) is at most the wall time since it plus 2 s, a report's growth is clamped to `reachAt` from that record's biomass (`boundBiomass`) over the active time since it, and a lock-in claim (`clampClaim`) over the wall time since it. Every path that writes a record of the connection's creature passes the life through `recorded(life, t)` (a checkpoint, a death, a mating, a settlement); a new binding (sign-in, genesis, promote, restore) starts from the head. A mating's records take the session's last report, so the client reports just before a court or an accept (`MateDeps.fresh`), or the next bounds would cut the growth it played since. Ticks claimed beyond the wall time since the binding (`startT`) plus 2 s are `clock-too-fast`. A mating also needs the maturity size (`LifeState.matureBiomass`, from `matureBiomassOf` under the object's scales), which `ownRefusal` checks when the view carries it.
- The audit (`worker/audit.ts`, M9 T8): `FLAG_KINDS` is the one catalogue of flag kinds, each documented where it is raised, and each raised through `hub.ledger.audit.raise(kind, { owner, creature, key, t })`, one row per kind and request (`key`: a request hash, an encounter, a player, a commitment or a mate ask) or per kind and creature, however often it repeats. `replay` is an owner-signed request for a head its chain has moved on from (`movedOn` in `ledger.ts`; the refusal stays `conflict`), a genesis ask whose creature already came, or a mate ask whose nonce a commitment used; an accepted request sent again keeps its idempotent answer and no flag. `GET /v1/audit` (`Authority.audit`, metered and 503 `busy` past 80% of the budget as proof reads are (`meterRead` in `proof.ts`), edge-cached 5 min through `edgeCached` in `index.ts`) counts the flags by kind for the UTC day and since `world.reset_at`, with no ids.
- Admission (`worker/usage.ts`, `canAdmit` in `worker/sessions.ts`): `MAX_SESSIONS` and `DAILY_REQUEST_BUDGET` are `vars`; a hub test sets them on the live object's `env` (`worker/queue.test.ts`). A queued socket has phase `queued` in its attachment and costs no SQLite writes.
- `LIFESPAN_SCALE` and `MATING_SCALE` (fixture mode only, with `DRAND_SOURCE=fixture`) shorten the lifespan, and maturity, cooldown, the repeat window and the restore minimum; they are read only through `scalesOf(env)` (`worker/mating.ts`), which the shared rulebook's gates (`src/ledger/gates.ts`) take, and `tools/worker-bundle.test.ts` guards that. Hub tests set them on the live object's `env` (`worker/mating.test.ts`). A courtship's invitation lives in the courting socket's attachment (`court`), never in SQLite; `worker/mating.ts` must export nothing that edits a stored round.
